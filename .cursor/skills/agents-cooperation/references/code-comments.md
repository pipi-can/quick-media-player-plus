# 代码注释怎么写

## 原则

注释是给**别人**看的——下一个 agent，和 review 代码的人（比如 `ren`）。判断标准只有一条：

> **别人只读注释，能不能明白你当时在想什么？**

所以：

- 写**为什么**，不写**是什么**。代码本身已经说了"是什么"。
- 写代码里**看不出来**的东西：为什么这么选、有什么约束、踩过什么坑、哪里不能动。
- **中文**，和工程其它注释保持一致。
- 宁可少而准，不要多而废话。

## 反例 → 正例

### 1. 复读机式注释

```cpp
// 反例：注释只是把代码翻译成中文，等于没写
// 设置音量为 percent
setVolume(percent);

// 正例：说清楚这个值是什么量纲、为什么这么处理
// percent 是 0~100 的整数（QML Slider 直接给的值）；
// player 内部统一用 0.0~1.0 的 float，这里做一次换算，别在各处重复换算。
setVolume(percent / 100.0f);
```

### 2. 解释"为什么"，而不是"做了什么"

```cpp
// 反例：读了代码就知道的事
// 如果队列为空就返回
if (queue.isEmpty()) return;

// 正例：解释这个判断背后的原因——后来者才敢改/不敢改
// 队列为空还必须直接返回：下面会读 queue.first()，
// 空队列时那是未定义行为。这里不能改成断言，因为正常关闭播放器时也会走到这。
if (queue.isEmpty()) return;
```

### 3. 单个值的含义，要写单位 / 量纲 / 取值范围

```cpp
// 反例
int m_timeout = 300;

// 正例
// 歌词请求超时，单位毫秒。歌曲很短时也要能拉到，所以给了 5 分钟。
int m_timeout = 5 * 60 * 1000;
```

### 4. 类 / 文件的头注释：说清楚职责和边界

```cpp
// 反例：等于把类名再说一遍
// LyricFetcher 类

// 正例：一句话说清它管什么、不管什么、和谁配合
// 按当前播放的歌曲拉在线歌词并缓存。
// 它只负责"拿到歌词文本"，不负责滚动、渲染、和播放进度对齐——
// 那些在 QML 侧，见 qml/layouts/LyricView.qml。
// 匹配规则见协作块 #11（agents-cooperation/lyrics/在线歌词实现思路.md）。
class LyricFetcher : public QObject { ... };
```

最后那行"见协作块 #11"很有用：**代码和思路记录互相指路**，review 的人顺着就能看到当初的设计。

### 5. 有坑的地方必须留注释

```cpp
// 反例：什么都没说，后来者会顺手"优化"掉
QThread::msleep(50);

// 正例：说清楚这个看起来多余的东西为什么在
// 这里必须等一拍：媒体探针是异步起线程的，不等的话 duration 还是 0，
// 后面算进度条会除零。别删这行。
QThread::msleep(50);
```

### 6. TODO 要有原因和条件

```qml
// 反例：谁都不知道什么时候能删
// TODO: 优化

// 正例：写清楚为什么先这样、什么条件下该改
// TODO: 现在每次切歌都重建整个 ListView，歌曲数量上到几千会卡。
//       等播放列表支持虚拟滚动后再换成增量更新。
```

## 注释和协作记录的分工

| 写在哪 | 写什么 |
| --- | --- |
| 代码注释 | 这一行 / 这一个函数**局部**的道理：单位、边界、坑、不能动的地方 |
| 块的 `[Comments]` | 这个功能**整体**的思路：拆成哪几块、关键取舍、接口约定 |
| commit 正文 | **这一次**改了什么、为什么这么改（和 `[Comments]` 对齐，但讲本次） |

三者不重复：注释管"这行为什么这样"，块管"整体怎么想"，提交管"这一步干了啥"。

## 自检

写完注释，问自己三句：

1. 一个**没看过这段代码**的 agent，只读注释能接着往下改吗？
2. 一个**review 的人**，只读注释能判断这里对不对吗？
3. 有没有哪句注释，删掉之后别人反而更容易看懂？（那就是废话，删了）
