# 常见疑问与边界情况

> **会翻车的地方**（撞号、幽灵块、全角冒号、rebase 掉 sha……）单独整理在 [pitfalls.md](pitfalls.md)，那份是实测出来的坑，优先看。

## 触发相关

### Q：仓库不是 git 仓库怎么办？

先问用户。这套流程的"哪次提交实现了它"完全依赖 git（`Coop-*` trailer、`[GitCommitIds]`）。要么让用户 `git init`，要么退化成只写块、`[GitBranch]` / `[GitCommitIds]` 永远 `null`——但要跟用户讲清楚：这样就没有提交线索了。

### Q：我改的是文档、配置、脚本，不是代码，也要走流程吗？

**看改动的性质，不看文件后缀**——先过三问（见规则文件第一节）：**用户能看到的行为变了吗？别人依赖的东西变了吗？你有取舍吗？**

- 改 `CMakeLists.txt` 加一个构建目标、改一个公共脚本的逻辑、改配置项的默认值 → **要登记**（别人依赖的东西变了）。
- 只是改注释/文案/格式，或修一行错别字 → **不用登记**，提交正文带 `Coop-Skip: <原因>` 即可。

**判断标准是"涉及功能 / 接口 / 取舍"，不是"改的是不是 .cpp"。**

### Q：只改界面文案呢？（比如按钮"确定"改成"确认"）

**看这行文案会不会改变用户对行为的预期**：

- 同义替换、措辞微调（"确定"→"确认"、"加载中"→"正在加载"）→ **不用登记**，`Coop-Skip: 界面文案同义替换`。
- 文案变了、**用户的行为预期也跟着变**（按钮"取消"改成"删除"、默认选项的说辞换了、警告语去掉）→ **要登记**：这已经是交互语义的改动，不是排版。
- 文案本身是**功能的一部分**（i18n 的 key、协议字段名、错误码对应的提示）→ **要登记**。

> 一句话：**改字不用，改意思要**。拿不准就按"要登记"处理，或者问用户。

### Q：只改一个错别字 / 空格呢？

不用登记。这类改动没有取舍、没有行为变化，`Coop-Skip: 修错别字` 即可。

### Q：只读代码、只回答问题呢？

不用走。没有文件改动就没有协作记录要写。

### Q：我改了 `.gitignore` 这种一行的小改动呢？

**分情况**：

- 加一行忽略规则、跟行为无关 → **不用登记**，`Coop-Skip: 忽略构建产物` 就行。
- 但如果这行会**改变代码行为**（例如把某个已跟踪的文件排除、改发布包含范围）→ 要登记。
- 小改动**要登记**时也不必硬编一个块：能**续写**相关块就续写，提交消息里写清思路即可。

## 块的组织

### Q：一个功能改了很多轮，要不要每轮新开一个块？

不要。**同一条思路的延续 = 同一个块**，只是往 `[GitCommitIds]` 数组最前面不断插新的 sha。块的 `[Comments]` 里也顺势补充"后续补充（谁，见 <sha>）"。

什么时候才新开块？**思路换了**：推翻重做、或者一个明显独立的新功能（比如队列里原来只做顺序播放，这次要加一整套"智能推荐"）。

### Q：分不清该复用还是新开？

问用户。这是规则里明确要求问的情况之一。给建议时按这个标准：**后来者看到 Title 时，会不会认为它们该一起读**。会 → 同一个块；不会 → 新开。

### Q：用户提了个新功能，`agents-cooperation/` 里没有对应的块？

那这就是**新功能**，**不许直接开写**。顺序是：

1. 告诉用户"没找到相关的块，看起来是新功能"；
2. **问要不要建块**，并把要写进块的信息一次问齐：文件夹名 / 标题 / 目标 / 边界 / 落点（涉及哪些目录文件）/ 约束 / 验收标准；
   —— 按工程现有习惯**先拟好建议**，让用户点头就行，别让他从零想；
3. 用户确认 → `coop-new-block.sh` 建块 → **把上面这些写进 `[Comments]`**；
4. 到这一步才动代码。

**块里的思路是动手之前的共识，不是写完之后的总结。** 正反例见 [asking-users.md](asking-users.md#新功能动手之前必须问一次并把答案写进块)。

### Q：用户说"这个不用建块"呢？

听用户的，但**先把后果说清楚**："不建块的话，这次改动在 `agents-cooperation/` 里没有任何记录，后来者不知道有这个功能，也不知道当初的取舍。"用户仍坚持就照做，并在回复里说明。

代码**照旧要提交**（"每次改文件都要提交"是另一条硬规则）。这种提交没有 `Coop-Block`，正文带一行原因即可通过 `commit-msg` 钩子：

```
feat(playback): 音量弹窗

（按用户要求，本次不登记协作块，只实现。）

Coop-Skip: 用户明确要求不建块
Coop-Author: opencode-agent
```

装钩子之前的老仓库、或者写了没法过钩子的消息，才退回用 `git commit --no-verify`。别因为用户拒绝了块就不提交。

### Q：思路被推翻了怎么办？

新开一个块，写明"取代 #<旧编号>，原因……"；再问用户是否把旧块置 `[Valid]: false`（**作废要用户点头**）。别直接删旧块——历史思路有参考价值，`[Valid]: false` 就是它的归宿。

### Q：一个提交同时服务两个块怎么办？

不行。**一个提交只服务一个块**，因为 trailer 只能写一个 `Coop-Block`。真有两个块要改，拆成两次提交。

### Q：块太多了，扫描很累怎么办？

这是 `[Title]` 的锅。Title 必须写到"一眼能判断相不相关"，比如：

- 好：`播放队列实现思路（PlayList 单例 + 两条队列模式）`
- 差：`播放相关`

另外功能文件夹本身就是第一层过滤：`playback/` vs `lyrics/` vs `theme/`，先按文件夹筛，再按 Title 筛。

## 字段

### Q：`[Author]` 写谁？一个块被多人续写过呢？

`[Author]` 写**最初写下这个块的人**。后来续写的人**不改** `[Author]`，而是在 `[Comments]` 里加一段：

```markdown
  ---
  后续补充（opencode-agent，见 d9fe736）：
    - 补了 XXX。
```

理由：`[Author]` 回答"这个块从哪来"；"哪一次是谁做的"由每次提交的 `Coop-Author` trailer 回答。两个信息各管一件事，不要混。

### Q：agent 署名该写什么？

`<工具名>-agent`：`cursor-agent`、`opencode-agent`、`claude-agent`……**必须以 `agent` 结尾**，脚本靠这个区分 AI 和人类。人的名字不能以 `agent` 结尾。

### Q：人类块连 `[Author]` 都没写呢？

`get-index.sh` 会把它列成 `[Author: (缺 [Author])]`。这时**先问用户这是谁写的**再补；补不了就写 `unknown`，但要在块的 `[Comments]` 里说明。

### Q：`[Index]` 撞号了怎么办？

先确认是"真的撞"还是"有人手写了不属于自己的号"。以**先提交的为准**，后到的改成 `get-index.sh` 给的下一个号，并在提交消息里说明"修复块编号冲突"。别两边都留着——同一编号指两个块会让 `Coop-Block` 反查失效。

### Q：人类块该写 `ren-1` 还是干脆不写？

都行。**不写**最省事——agent 扫到会自动补（`get-index.sh` 会给建议值）。要写就写 `<作者>-<序号>`，别写纯数字：纯数字参与全局最大值计算，会占掉 agent 的编号空间。

## 提交与 git

### Q：`[GitCommitIds]` 里的 sha 找不到了？

多半是 rebase / amend / squash 之后 sha 变了，或者分支被强推了。处理：`git log --grep='^Coop-Block: <编号>$'`（锚定，免得 `3` 把 `30` 捞进来）按 trailer 找**当前**的 sha，把失效的替换掉，并在提交消息里注明。

### Q：`[GitBranch]` 的分支被删了或者合并了？

不用改。提交对象还在仓库里，`git show <sha>` 照样能看。只有在分支彻底不存在、且你想提示后来者时，才在 `[Comments]` 里补一句"原分支已合并到 master"。

### Q：回写 commit 时又产生了一个新提交，这个也要登记吗？

不用。`[GitCommitIds]` 只登记**实现**提交；回写那次是纯登记操作，不占数组。但它的提交消息照样要带 `Coop-*` trailer。

### Q：提交历史是倒序的，从哪头看？

从**数组第一个（最新）**开始往回看。先看最新那步改成了什么样，再往前看它是一步步怎么演进来的。这样最快建立"现状 + 脉络"。

## 删模块 / 删功能

### Q：用户让我删掉一个模块 / 一个功能，直接删行不行？

不行。先搜出"思路依赖它"的块，再问用户：

```bash
./agents-cooperation/coop-find.sh <模块名或类名>
```

把清单摆给用户（哪几个块、为什么、将被置 `[Valid]: false`、**不会删除块**），**等用户明确同意**再改 `[Valid]`。
细节见 [SKILL.md 的「删模块 / 删功能」](../SKILL.md#删模块--删功能只作废不删除)。

### Q：删掉的是模块的一部分，不是整个，也要作废整块吗？

不一定。给用户两个选项让他挑：**A. 整块作废**；**B. 保留块，只在 `[Comments]` 里标注"X 已被移除，其余仍有效"**。
注意 **B 也要用户同意**——改别人的 `[Comments]` 属于"必须问"的情况。

### Q：搜完没有依赖它的块呢？

那就在回复里说一句"没找到依赖它的协作块"，然后照常删。**别默默删。**

## 编译验证

### Q：一定要编译吗？我改的是很简单的代码。

要。**没编译过就不算写完**——"应该能编译"不是验证。
真编不了（缺工具链 / 缺硬件）也要做到语法层面的检查（`clang++ -fsyntax-only`、`tsc --noEmit`、`python -m py_compile`），并明说"做到哪一步"。

### Q：构建命令从哪来？

按顺序：① `agents-cooperation/_repo/build.md`（团队确认过的）② 从仓库现状推断（`CMakeLists.txt` / `package.json` / `Cargo.toml` …）③ 问用户。
**确认之后写回 `_repo/build.md` 并提交**，别每次都重新猜。完整线索表见 [build-verify.md](build-verify.md)。

### Q：编译失败，但我觉得是环境问题不是我的问题。

先证明。用 `git stash` 把你的改动收起来再编一次：

- 同样的错 → 环境 / 既有问题；
- 不错了 → 就是你的锅。

**无论哪种，都要把命令 + 关键报错 + `文件:行` 报给用户**，别说"编译有点问题"就完了。

## 自评打分

### Q：每次都要打分吗？

**只要真的改了代码就打。** 纯文档 / 纯格式 / 只做块登记的提交，可以写一句"本次无代码改动，跳过打分"。

### Q：分数是给自己看的还是给用户看的？

**给用户看的**（还有 review 的人）。所以：每条扣分要指到 `文件:行` 并贴那段代码；最后必须补一句"我最不放心的三点"。
规则见 [code-review.md](code-review.md)。

### Q：我给自己打了 28 分（C 档），怎么办？

**先别提交**：把扣分点讲给用户，问"改还是接受"。用户说接受 → 提交，并把扣分项写进块 `[Comments]` 的遗留问题。
D 档（<24）就**先改再提交**，不用问。

### Q：分数要不要写进协作块？

**不新增字段**，块格式不动。B 档的扣分项、以及**没做到的验收项**，写进 `[Comments]` 的"遗留问题"那段就够了——那本来就是给人看的地方。

## 提交与 git 之外

### Q：用户要求 push 或者开 PR？

按用户说的做。默认**只提交到本地**。开功能分支时：`git checkout -b <feature>`，并把分支名写进块的 `[GitBranch]`,方便别的 agent 直接切过去看思路。

## 目录与工具

### Q：`agents-cooperation/` 还不存在？

跑一次 `coop-init.sh` 就铺好了：

```bash
.cursor/skills/agents-cooperation/assets/coop-init.sh
```

它会在仓库根目录建 `agents-cooperation/`，把脚本同步进去。然后再 `coop-new-block.sh` 建第一个块。别自己另写一份脚本。

> 里面的脚本是**副本**——正本是 skill 的 `assets/`。要改脚本就改正本，然后重跑 `coop-init.sh` 同步过去
> （它会报告改了哪几个），再用 `--check-sync` 对账。直接改副本的话，下次同步会被覆盖。

### Q：目录结构是死的吗？功能文件夹必须叫 `playback` 这种？

**结构是固定的，名字不是。** 固定的只有：目录叫 `agents-cooperation/`、一功能一文件夹、块的字段格式、脚本平铺在里面。

功能文件夹叫什么、文档叫什么，**按本仓库自己的习惯来**——`playback` / `theme` 只是示例，换一个工程就换成那个工程的功能划分（电商后台可能是 `orders` / `refund`）。关键是**别为同一个功能生造第二个名字**，否则后来者找不到。

### Q：块太多了，怎么少扫一点？

先按功能文件夹缩范围，再只看有效的：

```bash
./agents-cooperation/get-index.sh --valid --folder <功能>
```

`--folder` 只列该功能下的块，`--valid` 只列 `[Valid]: true` 的。这样一次要看的通常就一两个。

### Q：能不能把示例文档直接放进 `agents-cooperation/`？

不能。`get-index.sh` 会扫描 `agents-cooperation/` 下**所有** `.md`，把里面的块当成真块统计，编号就乱了。示例放本 skill 的 `references/` 里（就是你现在看的这类文件）。

### Q：两个 agent 同时改了同一篇 md？

以仓库里**最新的**为准（先 `git status` / `git pull` 看有没有别人改过）。有冲突就**停下来问用户**怎么合，别自己挑一边。能拆成不同功能文件夹的，尽量别让两个人在同一篇文档里打架。

### Q：`[Valid]: false` 的块要不要删掉？

不删。`false` 就是"留着但别参考"，它记录了"这条路走不通"——这本身是有价值的。删除会丢掉这个信息。

## 自检清单

动手前后快速过一遍：

- [ ] 改的是工作区文件 → 先过了"要不要登记"三问；只是看看 → 没走，对。
- [ ] 判断对了：**涉及功能 / 接口 / 取舍 → 建/续写了块**；**纯文案 / 注释 / 格式 / 笔误 / 纯登记 → 正文带 `Coop-Skip: <原因>`**（没拿它当挡箭牌）。
- [ ] 用 `get-index.sh --valid --folder <功能>` 缩过范围，没全盘扫。
- [ ] 只读了有效且相关的块，无关的没浪费时间。
- [ ] **是新功能的话**：先问过用户要不要建块、要了必要信息，并且**信息先写进了 `[Comments]` 才动手写代码**。
- [ ] **要删模块的话**：用 `coop-find.sh` 找过依赖它的块，清单报给用户了，**用户同意了才置 `[Valid]: false`**（块没删）。
- [ ] 顺着已有思路写，没有自己另起一套。
- [ ] 该问的都问了，没有臆想的地方。
- [ ] 代码注释按"别人看得懂"写的（见 [code-comments.md](code-comments.md)）。
- [ ] 新块用 `coop-new-block.sh` 建的（编号没手算、没撞）。
- [ ] **编译/构建跑过了**（编不了就说清做到哪一步、为什么）。
- [ ] **自评打分做完了**：验收对照 + 四个维度 + 扣分点指到 `文件:行` + 最不放心的三点。
- [ ] 提交前跑过 `coop-lint.sh`，没报错。
- [ ] 提交消息有标题、有思路、有 `Coop-*` trailer。
- [ ] `coop-record.sh` 回写完成，`[GitCommitIds]` 最新在最前、`[GitBranch]` 是真实分支名。
- [ ] 改过别人的 `[Comments]` / 作废过块 → 提交消息里写明了。
