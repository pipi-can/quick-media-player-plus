# 什么时候问、怎么问

规则里最硬的一条：**不清楚就问，不要臆想**。这份文件说清"什么算不清楚"和"怎么问才让人好回答"。

## 为什么这条最重要

agent 猜错一次，代价不是多写几行代码，而是**给协作目录里留了一条错的思路**。后来者照着错的思路继续写，错误会复利放大，而且很难发现——因为文档看起来"有据可依"。

所以：**宁可多问一句，不要多写一行。**

## 必须停下来问的情况

| 情况 | 例子 |
| --- | --- |
| 和已有有效块的思路对不上 | 用户说"音量存 QML 就行"，但块 `#10` 约定"音量挂 player 单例" |
| 类 / 模块的**职责**没说清 | 用户只说"写个 PlayList 类"，没说它管什么、谁用它 |
| **放哪个目录 / 文件**没说清 | "加个歌词模块" —— 放 `includes/lyrics/` 还是 `sources/network/`？ |
| 两个有效块的思路**互相矛盾** | `#3` 说单例，`#7` 说注入 |
| 分不清**复用块**还是**新开块** | 是给 `#3` 加一条，还是这个功能该单独开 `#12`？ |
| **新功能**：`agents-cooperation/` 里找不到对应的块 | **必须问**：要不要为它新建协作块 + 建块要写进去的信息（见下节） |
| 要**作废**某个块 | 把 `#9` 置 `[Valid]: false` 之前 |
| 要**改**某个块的 `[Comments]` | 用户否掉了原思路时 |
| 需求本身有多种合理解读 | "做个播放列表" —— 是队列还是 UI 列表页？ |

反过来说，**这些不用问**：

- 用户已经明确说了的（别再确认一遍）。
- 工程里已有惯例、且没有冲突的（比如照现有单例写法，不必问"要不要用单例"）。
- 纯粹的实现细节，怎么选都不违反已有思路的（比如变量取名）。

## 怎么问

好的提问有三个特征：

1. **一次问完**，别挤牙膏式一问一答三轮。
2. **给出你的建议和理由**，让用户能"点头"而不是"重新想"。
3. **把影响说清楚**，尤其是"这会和已有块冲突"这种事。

### 正例

> 音量弹窗有几个点想确认，我按工程现有约定给了建议：
> 1. 音量值挂 `player` 单例（加 `volume` 属性）——和块 `#3`"播放相关只走单例"一致。可以吗？
> 2. 弹窗放 `qml/layouts/VolumePopup.qml`，跟工程现有 `layouts/` 约定一致。行不行？
> 3. 拖动是实时改音量，还是松手才生效？我倾向实时。
>
> 你回个"都行"我就开写。

### 正例（发现冲突）

> 提醒一下冲突：`agents-cooperation/playback/播放控制实现思路.md` 的块 `#10` 约定"音量挂 player 单例"，
> 你现在说的"存 QML 里就行"和它冲突。怎么处理？
>
> A. 按你说的来，我同时改掉 `#10` 的 `[Comments]`，并在提交里写明"协作块 10 的 Comments 被修改"；
> B. 还是按 `#10` 老思路来，不动文档；
> C. 你其实想推翻 `#10` → 我新开一个块，并把 `#10` 置 `[Valid]: false`。

### 反例

> 用户：给播放页加个音量弹窗。
> agent：（默默新建 `AudioCtx` 单例、放 `qml/popups/`、松手才生效）…… 做完了。

问题：三项全是猜的。`#3` 的约定被无视了，弹窗目录也和工程不一致，以后没人知道当初为什么这么放。

### 反例

> 用户：帮我加个在线歌词。
> agent：请问歌词要显示在哪里？

问题：只问了最容易想到的一点，没问歌词源、放哪个目录、怎么匹配、要不要缓存——用户还得被迫第二轮、第三轮。**一次把该问的问完。**

## 新功能：动手之前必须问一次（并把答案写进块）

流程第一步是"去 `agents-cooperation/` 找同功能的块"。**找不到 = 这是个新功能**，这时不许直接开写，也不许自己起个名字就开干。必须：

1. 先告诉用户"没找到相关的块，看起来是个新功能"；
2. 问用户**要不要为它新建协作块**——同时给出你建议的文件夹名和标题，让用户点头就行；
3. 一次把建块要写进 `[Comments]` 的信息问齐：

   | 要问的 | 为什么要问 |
   | --- | --- |
   | 功能文件夹叫什么 | 定位靠它，乱起名字后来者搜不到 |
   | 一句话标题 `[Title]` | 后来者靠它判断相不相关 |
   | 目标 / 边界（做什么、不做什么） | 防范围蔓延，也防后来者顺手套别的功能 |
   | 落在哪些目录 / 文件、涉及哪些模块 | 防猜错位置 |
   | 必须沿用的约定、已知约束 | 防和已有块打架 |
   | 怎么算做完（验收标准） | 防"做完了"各说各话 |

4. 用户确认后：`coop-new-block.sh` 建块 → **把上面这些写进 `[Comments]`** → 然后才动代码。

也就是说：**块里的思路不是写完代码的总结，是动手之前的共识。** 先落共识，再落代码。

### 正例

> 我在 `agents-cooperation/` 里没找到跟"在线歌词"相关的块，这看起来是个**新功能**。开写之前想跟你确认几件事（我按工程现有习惯给了建议）：
>
> 1. **要不要建协作块？** 建议建（新建的块编号和目录我来分配）。
> 2. **文件夹名**：`lyrics`（英文小写，和 `playback` / `theme` 一个风格）。行吗？
> 3. **标题**：`在线歌词搜索与滚动同步`。够不够准确？
> 4. **目标 / 边界**：只做"搜索 + 按播放进度高亮"，不做歌词编辑、不做整轨离线下载。对吗？
> 5. **落点**：歌词拉取放 `sources/network/`，显示组件放 `qml/layouts/LyricsView.qml`。可以吗？
> 6. **约束**：歌词请求要不要跟着播放器走同一个网络单例？（已有块 `#3` 约定"网络只走单例"）
> 7. **验收**：切歌能自动匹配、进度高亮不漂移，就算做完？
>
> 你回个"都行"，我就建块、把上面这些写进 `[Comments]`，然后开始写代码。

### 反例

> 用户：帮我加个在线歌词。
> agent：（直接开写，边写边想）……

问题：没问要不要建块、没问放哪、没问边界，协作目录里**一条记录都没有**。后来者既不知道这个功能存在，也不知道当初为什么这么做。

### 用户说"不用建块"怎么办

**听用户的，但先把后果说清楚**，再照做：

> 提醒一下：不建块的话，这次改动在 `agents-cooperation/` 里就没有任何记录——后来者（包括别的 agent）不知道这个功能存在，也不知道当初的取舍。确定不建吗？
>
> 还是说"要建、只是别问这么细，按工程惯例来"？后者我现在就开写。

- 用户仍坚持"不建" → 照做，并在回复里写明"按你要求，本次未登记协作块"。
- 代码**照旧要提交**（"每次改文件都要提交"是另一条硬规则）。这种提交没有 `Coop-Block`，在正文带一行
  `Coop-Skip: 用户明确要求不建块` 就能过 `commit-msg` 钩子（钩子两种都认）。只有写不了这行时才用 `git commit --no-verify`。
- **不要**因为用户拒绝了块，就偷偷跳过提交。

## 删模块 / 删功能：动手之前必须问一次（"作废块"）

用户说"把 X 去掉"，或者你自己判断某个模块该删的时候——**先找出思路依赖它的块，报给用户，等同意，再动**。
块**只置 `[Valid]: false`、绝不删除**（删了编号会被回收，`Coop-Block` 反查就串台了）。

先搜：

```bash
./agents-cooperation/_tools/coop-find.sh <模块名 / 类名 / 文件名>
```

### 正例

> 这次要删掉 `AudioCtx`（`sources/audio/AudioCtx.*`）。
>
> 下面两个块的思路依赖它，将被置为 `[Valid]: false`（**不会删除块**，只是不再作为参考）：
>
> | 块 | 标题 | 文件 |
> | --- | --- | --- |
> | `#3` | 播放控制（Player 单例 + 状态机） | `playback/播放控制实现思路.md` |
> | `#7` | 音频后端切换 | `playback/播放后端实现思路.md` |
>
> 同意的话我就：① 把这两个块置 `false`，并各自在 `[Comments]` 末尾记一句"因删掉 AudioCtx 而废弃（opencode-agent，见 `<sha>`）"；② 提交消息写明"作废块 #3 #7"。不同意就告诉我保留哪个。
>
> 另外：只删掉 `AudioCtx` 的一部分（不是整个）的话，你也可以选"保留块、只在 `[Comments]` 里标注哪部分被移除了"——你说哪种。

好在哪：**先摆事实（搜到什么）、再说后果（置 false 而不是删）、给出动作（怎么写、提交怎么写）、留了退路（保留哪个 / 部分删除怎么办）**。用户一句话就能拍板。

### 反例

> agent：（直接删 `AudioCtx`，顺手把 `#3`、`#7` 置成 `false`，提交）……好了，删掉了。

问题有三处：① 没问就动别人的块；② 可能漏了依赖它的块（只搜了一个关键词）；③ 后来者看到 `[Valid]: false` 也不知道**为什么**废的。

### 找不到依赖它的块呢

也要说一句"搜过 `AudioCtx`，没有依赖它的协作块"，然后再删——**别默默删**。

（更细的多选项/部分删除情形见 [SKILL.md 的「删模块 / 删功能」](../SKILL.md#删模块--删功能只作废不删除)。）

## 用户回答"你看着办"的时候

那就按**已有块的思路 + 工程现有惯例**来，并在块的 `[Comments]` 里写清楚：

```markdown
[Comments]:
  ...
  用户表示按工程惯例即可，未指定 <具体项>，本次按 <实际做法> 处理。
```

将来想改的人能一眼看到"这里当初是 agent 自己定的"，而不是以为用户拍过板。
