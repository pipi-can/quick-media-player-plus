# 代码验收与自评打分

**每次真的改了代码，提交前都要按这份细则给自己打一次分，并把结果表发给用户。**
（只改文档 / 只做登记 / 纯格式化的提交，可以只写一句"本次无代码改动，跳过打分"。）

打分是**给用户看的产出**，不是内部思考。所以：

1. **每条扣分必须指到 `文件:行` 并贴那段代码**——没证据的扣分等于没扣。
2. **不适用（N/A）的检查项不计分**：该维度按"实得 ÷ 可评满分"折算成 10 分制（见下面「三、怎么算分」）。折算比"N/A 直接记 2 分"更诚实——不然整维 N/A 就会白拿满分。
3. **分数可以被用户推翻**。用户说"这项我不在意"，就按用户的判断调，但要在回复里说明"按你的意思，XX 项不计"。
4. **不许给自己满分糊弄过去**（除非真的一条都挑不出来），并且必须补一句"我最不放心的三点"——**这句话比分数有价值**。

> **默认四个维度等权**（各 10 分）。如果本仓库的评审重点明显不同（比如纯 UI 工程想压低"安全性"、后端服务想加重它），
> 就在 `agents-cooperation/_repo/build.md` 里加一小节写明本仓库的权重，agent 按它算并在表里注明"按本仓库权重"。
> 不要各自临时改权重——写下来，才是共识。

---

## 一、先做"验收对照"，再打分

打分前，先把块里 `[Comments]` 写的**验收标准**逐条对照一遍（没有验收标准就跳过这一节，并说明原因）：

```
## 验收对照（对照协作块 #3 的验收标准）
- [x] 切歌能自动匹配歌词
- [x] 进度高亮不漂移（实测 ±40ms）
- [ ] 歌词来源只做了本地缓存，在线源没做 → 记进块里的遗留问题
```

**这一节是"功能有没有做到"，评分是"代码写得好不好"——两件事，都要说。**

---

## 二、四个维度（各 10 分，总分 40）

每个维度 **5 个检查项 × 每项 2 分**：满足给 2、部分满足给 1、不满足给 0。

### D1 可读性（10 分）—— 只看注释和代码本身，不看功能对不对

| # | 检查项 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- | --- |
| 1 | 注释讲**为什么** | 关键决策 / 约束 / 坑都有原因说明 | 有注释，但一半是在复述代码（"// 设 x = 1"） | 复杂逻辑一行注释都没有 |
| 2 | 命名自解释 | 类 / 函数 / 变量看名字就知道职责 | 个别名字含糊（`data2`、`tmp`） | 大量 `a` / `b` / 拼音缩写 / 无意义编号 |
| 3 | 结构可扫 | 函数不超一屏、嵌套 ≤ 3 层、职责单一；无死代码 | 有个别长函数或深嵌套 | 大段注释掉的代码 / 死代码 / 一个函数干五件事 |
| 4 | 困难处有导引 | 魔法数有名字、复杂表达式有拆解、外部约定有出处 | 有一处没交代 | 一堆裸魔法数 / 外部依赖来历不明 |
| 5 | 能指回思路 | 代码里写 `见协作块 #N`，或与 `[Comments]` 的说法一致 | 大致一致但没指路 | 代码和块里写的思路矛盾 |

### D2 最小实现与合理性（10 分）—— 核心是"够不够小、有没有必要"

| # | 检查项 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- | --- |
| 1 | 不做没要求的事 | 只做用户要的 | 顺手多改了一点点 | 镀金：自己加功能 / 顺手大重构 |
| 2 | 复用已有设施 | 用了工程既有组件，和已有块约定一致 | 有点重复但情有可原 | 重复造轮子 / 和已有块约定打架 |
| 3 | 改动面最小 | 只碰必要的文件与行 | 多改了几个无关行 | 夹带大面积格式化 / 重排 / 无关文件 |
| 4 | 复杂度匹配需求 | 没有为一次性需求引入抽象层 / 新依赖 / 配置项 | 有一处过度设计 | 为小需求引入新框架 / 新依赖 / 一堆可配置项 |
| 5 | 无残留 | 干净 | 有 TODO 但写了原因和条件 | 调试打印、临时开关、没用到的 import / 变量 |

### D3 协作风格一致性（10 分）—— 关键是"像不像这个仓库本来就有的代码"

| # | 检查项 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- | --- |
| 1 | 命名 / 布局跟随仓库 | 大小写、前后缀、目录归属都和现有代码一致 | 个别不一致 | 自己另立一套命名法 |
| 2 | 错误 / 日志 / 资源管理一致 | 沿用仓库既有方式 | 略有出入 | 混进另一套体系（比如突然用异常而仓库用错误码） |
| 3 | 格式化一致 | 缩进 / 换行 / 空行 / import 顺序与同目录文件一致 | 小出入 | 和同目录文件风格明显不同 / 过不了工程的格式化工具 |
| 4 | 注释语言一致 | 和工程一致（本工程以中文为主） | 有零星英文 | 整段另一种语言 |
| 5 | API / 用法风格一致 | 新接口的命名、参数习惯、错误返回方式跟仓库既有 API 一致（getter / setter、信号槽、命名约定……） | 有一处不跟 | 自创一套接口风格，和周边明显不同 |

> **"死代码 / 注释掉的代码"只在 D1-3 扣一次**（可读性），D2-5 只管"这次有没有留下调试残留"——别同一个问题扣两次分。

### D4 安全性（10 分）

| # | 检查项 | 2 分 | 1 分 | 0 分 |
| --- | --- | --- | --- | --- |
| 1 | 外部输入校验 | 文件 / 网络 / 命令行 / 用户输入都校验了，或写明了为什么不用 | 部分校验 | 直接信任外部数据 |
| 2 | 无硬编码敏感信息 | 干净 | 有可疑的本地路径 | 密钥 / token / 密码 / 内网地址写死在代码里 |
| 3 | 危险操作有护栏 | 删除 / 覆盖 / 执行命令 / 写系统目录 / 发请求：有边界检查 + 失败处理 | 有检查但不全 | 无脑执行 |
| 4 | 资源与生命周期 | 空指针 / 越界 / 泄漏 / 竞态 / 异常路径都考虑了；失败不留坏状态 | 漏了个别分支 | 明显会崩 / 会泄漏 / 会留半成品状态 |
| 5 | 权限与隐私最小化 | 不越权访问、不把敏感信息写日志或上传 | 有一点冗余日志 | 泄露隐私 / 越权 |

### 四维之外：过程要求（**不计入 40 分**，但提交时必须满足）

这些是"提交这件事"本身的规矩，和代码质量无关，所以不占分，只在表后面附一行"是否满足"：

- 一个提交只服务一个块（别把两个块塞进同一个提交）；
- 提交正文写清实现思路，尾部带 `Coop-Block` / `Coop-Folder` / `Coop-Author`；
- 不登记的改动带 `Coop-Skip: <原因>`。

## 三、怎么算分（含 N/A 折算）

每个维度 5 项 × 2 分 = 10 分。**不适用（N/A）的项不计分**，该维度按比例折算回 10 分制：

```
维度得分 = round( 10 × 实得 / 可评满分 )
```

> 例：安全性 5 项里 2 项 N/A（可评满分 6），实得 5 → `round(10 × 5/6)` = **8.3 → 8 分**。
> 表里那两行也要写出来，标 `N/A` 和原因（"本次没有外部输入"），而不是悄悄消失。

**总分 = 四个维度之和（满分 40）**，等级按总分判（见第五节）。

为什么要折算而不是"N/A 直接给满分"：整维 N/A（比如纯文档改动）会白送 10 分，把总分抬到一个看着好看、
其实什么都没验证的位置。折算至少让"没评的东西"不产生虚高的分。

## 四、输出格式（照抄这张表，填满它）

```
## 验收对照
（对照块里的验收标准，逐条打勾 / 说明）

## 自评打分

| 维度 | 得分 | 为什么给这个分 | 扣分点（指到 文件:行） |
| --- | --- | --- | --- |
| 可读性 | 8/10 | 命名清楚、结构可扫；但两处魔法数没解释 | -1 `Player.cpp:88` 里的 `1500` 没说明；-1 `Player.cpp:132` 的 `state & 0x3` 没有注释 |
| 最小实现与合理性 | 9/10 | 复用了 Player 单例，没夹带无关改动 | -1 `Player.cpp:200` 加了个没人用的 `debugDump()` |
| 协作风格一致性 | 7/10 | 命名和日志都跟了现有风格 | -1 注释用了英文（周边是中文）；-1 目录放错（应放 `sources/player/`）|
| 安全性 | 8/10 | 本改动没有外部输入；危险操作那 2 项 N/A（可评满分 6，实得 5 → 折算 8） | 无 |

| **总分** | **32/40（B）** | | |

## 过程要求
- [x] 一个提交只服务块 #10；正文有思路；带 `Coop-Block` / `Coop-Folder` / `Coop-Author`

## 我最不放心的三点
1. `Player.cpp:88` 的 1500ms 超时是拍脑袋定的，没有依据，切弱网设备可能不够。
2. 只编过，没在真机上跑过播放/暂停的实际切换。
3. `debugDump()` 是我加的调试口子，忘了删。
```

**扣分点那段代码要贴出来**（几行就够），不然用户没法判断你扣得对不对：

```cpp
// Player.cpp:88
if (elapsed > 1500) {   // ← 这个 1500 是什么？为什么不是别的值？
    reset();
}
```

## 五、等级与处置

| 总分 | 等级 | 怎么办 |
| --- | --- | --- |
| ≥ 36 | A | 直接提交 |
| 30–35 | B | 直接提交，但**把扣分项写进协作块 `[Comments]` 的"遗留问题"** |
| 24–29 | C | **先别提交**：把扣分点讲给用户，问"改还是接受" |
| < 24 | D | **停下来先改**：改完再走提交流程 |

### C / D 档和"每次改完都要提交"的关系（这条别理解错）

"每次改完工作区文件都要提交"是硬规则；C/D 档是**提交之前**的暂停点，两者不冲突——顺序是
**暂停 → 问用户（或先改）→ 再提交**。唯一要防的是"卡在暂停上，改动一直挂在工作区里没人知道"。所以：

- **C 档**：
  - 用户回话 → 按用户说的办（接受 → 提交并把扣分项写进块；要改 → 改完再评一次）。
  - **联系不上用户、但又必须交差 → 提交**，并且把话说全，别让扣分点静默消失：
    提交正文里写一行 `自评：28/40（C，扣分点见块 #N 遗留问题）`，把扣分项写进块 `[Comments]`，
    回复里也点明"这版是 C 档、扣分点是什么、建议下一步怎么改"。
- **D 档**：**先改**，改完（通常就上到 A/B 了）再提交。只有用户明确说"就这样提交"才带病提交——
  那就当成 C 档处理，把问题写进遗留。

分数不是目的，**"我最不放心的三点"才是**——那是留给后来者的真话。

## 六、常见扣分点速查（省得每次现想）

- **可读性**：裸魔法数、复述式注释、超过 60 行的函数、`a/b/tmp`、注释掉的代码块、没说明的 `#ifdef`。
- **最小实现**：顺手重构、加了没人用的接口 / 参数 / 配置项、"以后可能要用"的抽象、格式化整个文件造成大 diff。
- **一致性**：命名风格混用（camelCase / snake_case）、目录放错、日志用另一套宏、注释语言串了、接口风格另立一套。
- **安全性**：`system()` / `eval()` 拼字符串、路径拼接没做校验、`QProcess` 直接跑用户输入、把 token 写进代码或日志、删除前不确认、异常路径没清理临时文件。

**过程要求（不计分）**：一个提交一个块、正文有思路、带 `Coop-*` trailer。

## 七、和协作块的关系

- **B 档的扣分项**：写进块的 `[Comments]`，加一段"遗留问题（opencode-agent，见 <sha>）"。
- **没做到的验收项**：同上，写进遗留问题——**别让"验收没做完"这件事悄悄消失**。
- **改了别人的 `[Comments]`**：先问用户（规则里的硬要求）。
